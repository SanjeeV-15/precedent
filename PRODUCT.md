# Precedent - product spec (2026-11-18)

**One line:** Precedent is a decision memory for teams and AI agents. It turns a folder of meeting and decision notes into a Relate graph, so anyone (or any agent) can ask "is this still in force, what replaced it, and does my new proposal contradict anything we already decided?"

Target: Relate by Neo4j hackathon, submit Dec 10, 2026 (deadline Dec 11, 6pm PST).

## Why this product (and why we changed course)
A dry run showed that on simple lookups an LLM with the schema in its prompt writes correct Cypher at lower cost than a node-by-node cursor (see [docs/cursor-experiment.md](docs/cursor-experiment.md)). So we stopped trying to beat Cypher at easy questions and moved to a problem where a graph clearly earns its place: **multi-hop reasoning over relationships that text search cannot see** (replaced-by chains, dependencies on replaced decisions, scoped conflicts, aliases, ownership by someone who left).

## What it does
| Command / tool | Question it answers | Graph work |
|---|---|---|
| `precedent check "<proposal>"` | Which active decisions conflict with this? | `CONSTRAINS` stance and scope overlap, filtered to active decisions |
| `precedent why <decision or project>` | What led to this? | `SUPERSEDES` and `DEPENDS_ON` chains |
| `precedent stale` | What should we revisit? | Active decisions that depend on replaced ones, or are owned by someone who left |
| `precedent conflicts` | Where do we contradict ourselves today? | Pairwise conflict query over active decisions |
| MCP tools + agent skill | Same, from any agent | Relate's MCP server plus a skill file |

A decision is **active** when no later decision supersedes it. That is derived from the graph, never stored, so it can't drift out of date.

## How it uses Relate
- Folder of markdown notes is the source of truth (Obsidian opens it; hand edits work).
- Built into a single-file Relate store (`store/precedent.rl`), committed so judges can inspect it.
- Relationship types: `DECIDED_IN`, `MADE_BY`, `OWNED_BY`, `AFFECTS`, `CONSTRAINS` (with `stance` and `scope` edge properties), `SUPERSEDES`, `DEPENDS_ON`, `ATTENDED_BY`.
- Mode: single file (`.rl`) for portability; in-memory for tests.

## Data (fictional, safe)
Fernwood Robotics, a made-up warehouse-robot company: 30 decisions, 30 meetings, 8 people, 6 projects, 9 technologies = 82 notes, 298 relationships. All data is invented. Generated by `scenario/fernwood.py`. Planted cases: 3 real conflicts, 2 stale dependencies, 2 decisions owned by a departed person, 5 replaced decisions, an alias (Quanta DB / QuantaDB / Q-DB), and one false-positive trap (a "forbids" and an "allows" with different scopes that must NOT be flagged).

## Honest caveat to state in the README
The conflict logic relies on structured fields (`stance`, `scope`) captured in each decision note. In the demo those are written by the scenario generator. In real use a capture step (a human template or an agent) fills them in. The graph's value is what it does once that structure exists.

## Evaluation (the credibility piece)
Answer key computed in Python, independent of Cypher: `eval/answer_key.json` (14 questions now, target 25).
Arms, same model and effort:
1. **files**: agent can search and read the markdown files (grep and read).
2. **graph**: agent can run read-only Cypher on the Relate store (schema in prompt).
Optional third arm: graph plus the `precedent` tools.
Report per question type: exact-match rate, F1, tool calls, tokens, cost; 3 runs each; models Haiku 5.5 and Sonnet 5.5. Commit transcripts so `make eval-replay` reproduces the tables with no API key.
We report whatever it shows. Hypothesis: the graph arm wins on conflict, stale, alias and lineage questions; ties on simple active-filter ones.
